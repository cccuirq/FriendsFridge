# 演示与现场修改准备

线上地址：https://friends-fridge-jianghui.app.space

## 五分钟核心演示

1. 用 Google/GitHub 登录，首次创建用户名。说明联系邮箱与平台登录身份的区别。
2. 添加两种库存，其中一种保持 Private，一种设为 Friends。直接点击冰箱门开关，门默认关闭。
3. 用第二个真实账号搜索第一个用户名、发申请并接受。检查只有共享食材可见；发送消息。
4. 打开 Recipes，调整人数；比较 In my fridge、Borrow from friends 与 Buy within budget。借用模式展示数量与提供者，发送明确请求。
5. 在 Friends 接受并完成交接；检查双方数量变化、重复完成不会再次扣除，观察推荐更新。
6. 在预算模式查价，说明每组范围、网上非会员整包价、剩余量和查询时间。门店列表只提供地点，不能声称具有门店结算价。
7. 打开资料页导出个人 JSON。可展示菜谱创建、照片、分享接受与撤销作为补充。

首次真实识别需要服务可用及余额；失败时展示诚实错误并用手动添加继续。不要用未成功的调用声称识别已完成。

## 应能亲自解释的设计

| 问题 | 需要理解的代码与取舍 |
| --- | --- |
| 为什么不用原 MongoDB/密码登录？ | 用平台原生 Auth、SQLite DO 与部署，减少外部运维；原团队项目保留在根目录，迁移代码在子目录 |
| 如何保证交接只扣一次？ | `domain.ts` 检查状态及当前库存；`room.ts` 同步事务统一持久化；缓存只在事务提交后替换 |
| 为什么不信任前端 user_id？ | Worker 验证平台身份后设置内部 subject；业务层用当前账号判断归属与好友关系 |
| 查价断网后为什么不会重复收费？ | 浏览器先保存 UUID；服务端按所有者和条件指纹去重；恢复轮询同一任务；罕见供应商已启动而回写失败的分布式边界不承诺绝对 exactly-once |
| 为什么缺价不能返回零？ | 采购完整性决定是否有 total；只有所有缺口都有可靠报价时才参与预算推荐；已有库存无需采购 |
| 为什么需要整包取整？ | 所需量不代表可购买的分装量；向上取整包数，按包价计费，展示剩余量 |
| 下一步怎样扩大规模？ | 规范化并索引 SQLite 表、按群组隔离房间、增加历史保留策略；保持交接的事务边界 |

## 适合现场的小修改

先阅读错误并提出假设，再写能验证假设的测试，最后修改实现。例如调整报价 TTL 并验证失效；添加一种明确包装单位及反例；修改候选分组限制并确认下一组游标；在拒绝好友关系后验证共享库存不可访问。

申请者应在 [SUBMISSION.md](../SUBMISSION.md) 逐项记录自己确实验证或修改的内容。代理已经做的自动化工作与个人操作分开填写。
